# 16. TLS on peer and client connections

## Status

Accepted

## Context

Issue #46 (Phase 7, see [docs/ROADMAP.md](../ROADMAP.md)): traffic on
the wire — peer-to-peer and client-to-node alike — is plaintext today.
Anything that can reach a node's listening address can read or inject
`Publish`/`Subscribe`/`Hello`/`PeerAnnounce` traffic. This ADR resolves
#46's open questions:

- Which TLS library.
- What the certificate/trust model is.
- Opt-in or default-on.
- How this interacts with peer authentication (#47) — #46 explicitly
  flags that mutual TLS could double as #47's authentication
  mechanism, and asks for the two to be decided together rather than
  bolted on separately.

It also has to fit two constraints this project already committed to:

- **The shared port** (ADR-0009): client and peer connections aren't
  distinguishable until a `Hello` arrives, mid-connection, over
  already-framed application data. Whatever TLS policy the accept side
  applies, it has to apply *before* that — the same TLS config serves
  both kinds of connection.
- **Generic async framing** (ADR-0008): `thoth-mesh-core`'s framing
  and `thoth-mesh`'s handshake are generic over
  `futures_util::io::{AsyncRead, AsyncWrite}`, bridged from tokio via
  `.compat()`/`.compat_write()`. Adding TLS shouldn't need to touch
  either of those — only what feeds them.

## Decision

### Library: `rustls` + `tokio-rustls`, `ring` crypto backend

`rustls` over `native-tls`/OpenSSL, matching #46's own steer: pure
Rust, no system OpenSSL version to manage across platforms, and
already the de facto default in the Rust ecosystem. Within rustls's
pluggable crypto providers, `ring` over `aws-lc-rs`: `ring` doesn't
need `cmake`/`nasm` in the build toolchain, which matters for a
project whose CI and contributor setup (see CONTRIBUTING.md) is
currently just a stock Rust toolchain.

### New crate: `thoth-mesh-tls`

TLS setup is needed in two places that don't otherwise depend on each
other: `thoth-mesh-node` (accept *and* dial both need it) and
`thoth-mesh-cli` (dial only, and doesn't depend on `thoth-mesh` — the
federation crate — at all today, since a plain pub/sub client has no
use for `Membership`/`PeerDirectory`/gossip). Duplicating
certificate-loading and `rustls::ClientConfig`/`ServerConfig`
construction in both would mean security-sensitive setup code living
in two places that need to stay in sync by hand.

`thoth-mesh-tls` is a new, small crate depending only on
`tokio-rustls` and `rustls-pki-types`. It exposes:

- `load_certs`/`load_private_key`: PEM file loading, the one piece of
  I/O this crate does — via `rustls-pki-types`'s own `PemObject`
  trait, not the separate `rustls-pemfile` crate. `rustls-pemfile` was
  the initial choice here, but turned out to be unmaintained
  (RUSTSEC-2025-0134, flagged by CI's `cargo audit` job right after
  this PR opened) and is itself now just a thin wrapper around the
  same `rustls-pki-types` code — switching removed a dependency
  instead of adding one.
- `server_config(cert, key, ca) -> ServerConfig` and
  `client_config(ca, identity: Option<(cert, key)>) -> ClientConfig`:
  the trust/identity policy described below, built once at startup.
- `MaybeTlsStream`: an enum over `TcpStream` /
  `tokio_rustls::server::TlsStream<TcpStream>` /
  `tokio_rustls::client::TlsStream<TcpStream>`, implementing tokio's
  `AsyncRead`/`AsyncWrite` by delegating to whichever variant is
  active. This is what makes TLS an additive change rather than a
  rewrite: every call site that used to hold a `TcpStream` holds a
  `MaybeTlsStream` instead, and reaches `.compat()`/`.compat_write()`
  the same way it always did — plaintext and TLS connections are
  indistinguishable past this point.

This is the sixth workspace crate (see ADR-0002's layering, ADR-0014's
lockstep-versioned crate set) and gets published to crates.io
alongside the other five per that ADR's practice, as a separate manual
step once this lands.

### Trust model: one self-signed CA per mesh, optional client identity

A private mesh signs its own CA once (via `openssl` — documented in
OPERATIONS.md, not generated by thoth-mesh itself, matching the
project's existing "no config file, no built-in tooling beyond what's
strictly needed" minimalism) and issues every node a leaf cert from
it. This is the model #46 itself suggested as the fit for "a
single-operator/learning-project trust model" — no public CA, no
revocation infrastructure, just a shared trust anchor an operator
controls.

**Accept side (every connection, client or peer):** presents the
node's own server cert, and requests but does **not require** a client
certificate — rustls's `WebPkiClientVerifier` with
`allow_unauthenticated()`. This is the direct consequence of the
shared-port constraint: the accept side can't yet know if this will
become a peer link (which should identify itself) or stay a plain
client (which today has no identity concept at all, and Phase 7 isn't
introducing one for clients — that's #62). A connection that presents
a CA-signed cert is authenticated; one that doesn't still gets an
encrypted, working connection, exactly as unauthenticated as it is
today.

**Dial side, node-to-node (`peering.rs`):** always presents the
node's own cert as its client identity — a peer dialing another peer
*is* declaring itself a peer, so it always identifies itself — and
requires the far end's server cert to verify against the CA (standard
server auth, no "unauthenticated" escape hatch here). The same
cert/key a node uses to identify itself on accept is reused as its
client identity when dialing: one identity per node, not two.

**Dial side, CLI (`thoth-mesh-cli`):** `--tls-ca` alone enables TLS
(server-auth only — the CLI verifies the node it's talking to, same
as any TLS client); `--tls-cert`/`--tls-key` are optional and only
needed if the operator wants this client connection to be identifiable
later (#62, not enforced by anything today).

This gives #47 (peer authentication/allowlisting) exactly the hook it
asked for without this issue owning any of it: by the time a `Hello`
arrives, the connection may already carry a verified peer certificate
identity, available via `MaybeTlsStream::peer_certificates()`. #47's
allowlist logic can check it; #46 doesn't inspect it or enforce
anything beyond "chains to the CA if present at all."

### Opt-in, not default-on

TLS is off by default — every existing deployment is plaintext today,
same bridge posture as `--metrics-addr` (ADR-0013). `thoth-mesh-node`
needs `--tls-cert`, `--tls-key`, and `--tls-ca` given together to turn
it on (partial specification is a startup error, not a silent
fallback to plaintext); `thoth-mesh-cli` needs at least `--tls-ca`.
With none of these given, behavior is unchanged from before this ADR.

### Transport refactor: `tokio::io::split` replaces `TcpStream::into_split`

`connection.rs` and `thoth-mesh-cli`'s client loop currently hold
concrete `TcpStream`/`OwnedReadHalf`/`OwnedWriteHalf` types.
`TcpStream::into_split` is a `TcpStream`-only zero-copy split;
`MaybeTlsStream` doesn't have an equivalent. `tokio::io::split` (a
free function, generic over any `AsyncRead + AsyncWrite`) replaces it
everywhere a split is needed — `ReadHalf<MaybeTlsStream>`/
`WriteHalf<MaybeTlsStream>` instead of the `TcpStream`-specific
owned-half types, otherwise unchanged. `thoth-mesh-cli`'s client loop
doesn't split at all today (one handle used for both directions
sequentially) and doesn't start now either — just
`Compat<TcpStream>` becomes `Compat<MaybeTlsStream>`.

The Prometheus metrics endpoint (`metrics_server.rs`, ADR-0013) is
explicitly out of scope — it's typically scraped from a trusted,
private network by infra (Prometheus itself) rather than exposed the
way the mesh port is, and adding TLS there is a separate concern if it
ever turns out to matter.

## Consequences

Enabling TLS costs three new flags on the node and one-to-three on the
CLI, one new (small, focused) crate, and an operator-run `openssl`
walkthrough in OPERATIONS.md for standing up a CA and issuing certs —
no change to anyone not opting in. `MessageKind`, framing, and the
wire format itself (PROTOCOL.md) are untouched; TLS wraps the
transport underneath, it doesn't change what's on top of it.

The cost living forward: `thoth-mesh-tls`'s "client cert optional"
accept-side policy means TLS alone still doesn't answer "is this peer
allowed to join" — that's still #47's job, deliberately deferred, not
solved by wrapping the transport. An operator who wants every
connection authenticated (not just peer links) still has nothing to
enforce that at the client layer until #62. And `rustls`/`tokio-rustls`
are non-trivial new dependencies (crypto code, `ring`'s own build
requirements) for a project that has otherwise stayed deliberately
light — an accepted tradeoff for actual transport security, not a free
one.
